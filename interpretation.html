37  Evidence-guided biological interpretation

Statistical enrichment results are evidence to inspect, not biological conclusions by themselves. This chapter describes how to move from enriched terms, core genes, networks, expression trends, and prior knowledge to a transparent interpretation. AI assistance is presented as an optional evidence-synthesis layer after those checks, not as a replacement for the enrichment analysis or literature review.

Enrichment results identify terms and genes associated with the input, but they do not by themselves establish a mechanism. Interpretation therefore starts with the result object, core genes, background, database provenance, and any supporting expression or network evidence.

37.1 The interpret function

interpret() accepts enrichResult, gseaResult, or compareClusterResult objects and asks an LLM to organize the supplied evidence into a structured report. The report is a draft for evidence review, not a replacement for the enrichment test or literature validation.

The function requires an API key for a provider supported by aisdk. If model is not supplied, it uses the current model from aisdk::get_model() / aisdk::set_model(); an explicit model argument overrides that default for one call. The examples below use DeepSeek through DEEPSEEK_API_KEY, but other aisdk providers can be used.

library(aisdk)

# Credentials come from the environment; a local .env file works too
if (file.exists(".env") && requireNamespace("dotenv", quietly = TRUE)) {
    dotenv::load_dot_env()
}

# Set a session-wide default model. Any provider supported by aisdk works here;
# in CI the key is supplied as the DEEPSEEK_API_KEY repository secret.
set_model("deepseek:deepseek-v4-flash")

# Check the current default model
get_model()
[1] "deepseek:deepseek-v4-flash"
library(clusterProfiler)
library(DOSE)

# A self-contained enrichment result: `edo` is built offline from the demo gene
# list shipped with DOSE, so the example depends neither on a previous chapter
# (`edo` is defined in the enrichplot chapter) nor on a network service.
data(geneList, package = "DOSE")
de <- names(geneList)[abs(geneList) > 1.5]
edo <- enrichDO(de)

# Basic usage
# 'edo' is your enrichment result object
res <- interpret(edo)

if (interpret_failed(res)) {
    stop("interpret() returned no report -- check the API key and quota:\n",
         res$overview)
}
cat(render_interpretation_blocks(res), sep = "\n")

37.1.1 Entry points and inputs

The question decides which entry point to use; all four return a model-written draft that still has to be checked against the result object:

  • interpret() organizes enrichment evidence into a biological narrative;
  • interpret_agent() runs the Cleaner–Detective–Storyteller pipeline and returns conclusion, the answer to the question posed in context; prior makes it check another tool’s label, and review = TRUE adds an audit agent;
  • interpret_hierarchical() labels minor clusters while constraining them to the supplied major-cluster context;
  • interpret_dialogue() continues the conversation interactively.

The input can be one result object, a list of compatible objects, or a compareCluster result processed by cluster. For example, list(go_res, kegg_res) combines compatible knowledge sources, while a compareCluster result returns one report per cluster. The returned fields are structured so that reports can be checked, compared, and rendered consistently.

For single-cell data, the marker table can come from Seurat::FindAllMarkers() or another marker-calling method. Keep the cluster and gene columns, use the same identifier namespace in the marker and CellMarker tables, and pass the grouped markers through compareCluster() before annotation. The executable example below uses the repository-local CellMarker table so that it does not depend on a separate count matrix or a pasted annotation report. A complete Seurat marker workflow is available in the pbmc3k tutorial.

37.1.2 Cell Type Annotation

The cell-type example reads the local datasets/Cell_marker_Human.xlsx marker table, builds four marker profiles, runs compareCluster() with enricher(), and asks interpret_agent() which cell type each cluster most likely is — the question goes in context, and the answer comes back as conclusion — when DEEPSEEK_API_KEY is available.

    transmute(
        cell_name = .data[["Cell name"]],

    ) |>
    filter(
        !is.na(cell_name), !is.na(marker),

    T_cell = c("CD3D", "CD3E", "TRBC1", "IL7R", "LTB", "MAL", "CCR7", "LST1"),

    rbind,
    lapply(names(marker_sets), function(cluster) {
        data.frame(
            cluster = cluster,
            gene = marker_sets[[cluster]],
            stringsAsFactors = FALSE
        )
    })
)

cell_marker_enrichment <- compareCluster(
    gene ~ cluster,
    data = marker_table,
    fun = enricher,
    TERM2GENE = TERM2GENE_cell,
    pvalueCutoff = 1,
    qvalueCutoff = 1,
    minGSSize = 2,
    maxGSSize = 500
)

    cell_marker_enrichment,
    context = paste(
        "Human single-cell marker panels. Each cluster is a compact set of",
        "top marker genes and was tested against the local CellMarker database.",
        "Which cell type does each cluster most likely correspond to?",
        "Use the enrichment terms as supporting evidence, but prefer markers",
        "that distinguish closely related cell types, and explain which",
        "supplied markers and cell-marker terms support the label."
    ),
    n_pathways = 12,
    max_tokens = 4096,
    temperature = 0.1
)

}

    }
}

37.2 Extended evidence inputs

interpret_agent() applies three sequential stages to an interpretation request:

  1. Term curation selects and organizes the supplied enrichment terms in the stated biological context; it does not rerun the enrichment test.
  2. Evidence inspection combines the result object with optional gene-level changes and interaction data to identify genes or modules that support each term.
  3. Narrative drafting writes the checked inputs into the structured interpretation fields used by the report and plotting methods.

The implementation refers to these stages as Cleaner, Detective, and Storyteller. They are components of one shared-model pipeline, not separate statistical analyses. The stages share one evidence bundle, and their output remains a model-generated draft that should be checked against the original result object.

context <- "scRNA-seq analysis of CD8+ T cells in tumor microenvironment, comparing exhausted and naive states."
res <- interpret_agent(edo, context = context)

37.7.1 Choosing a Model and Switching Provider

Model selection is delegated to aisdk. interpret() itself has no model registry and no provider logic: when model is left at its default (NULL) it uses whatever aisdk currently considers the default, and model = "provider:model" overrides that default for a single call.

library(aisdk)

# Session-wide default, used by every interpret() call that omits `model`
set_model("deepseek:deepseek-v4-flash")
get_model()

Calls that omit model use the session-wide setting selected with set_model(). Pass model for a one-off provider or model.

res <- interpret(edo, model = "openai:gpt-4o")

Credentials follow the same rule. aisdk reads each provider’s key from an environment variable: OPENAI_API_KEY, ANTHROPIC_API_KEY and GEMINI_API_KEY for the three providers bundled with aisdk, and the corresponding variable for the adapters in aisdk.providers (for example DEEPSEEK_API_KEY, which is what this chapter uses). Put the key in a project .Renviron or export it in the shell; interpret() never takes a key argument. If you never call set_model(), aisdk falls back to its built-in default, openai:gpt-4o – which is why the examples you may have seen elsewhere appear to use GPT-4o by default.

aisdk ships a catalogue of the providers and models it knows about:

list_models()            # every provider and model aisdk knows about
list_models("openai")    # just one provider

Model choice affects latency, cost, context capacity, and output variability. Fix the model when comparing reports, because different models can produce different summaries from the same input.

37.7.2 Multi-Model and Consensus Workflows

There is no built-in consensus or ensemble mode in interpret() or interpret_agent(). A call goes to exactly one model. interpret_agent() is a multi-agent pipeline, not a multi-model one: its three agents share a single model.

What you can do today is run the same input through several models and compare the reports yourself. Because model = is a per-call argument, this needs no extra machinery:

res_deepseek <- interpret(edo, model = "deepseek:deepseek-v4-flash")
res_gpt      <- interpret(edo, model = "openai:gpt-4o")

Each call is a separate, billable request, and the two reports will not be identical even for the same model (see below). A pragmatic middle ground is to use one model to write the report and a second, independent call only to criticise it: ask a different model whether every gene and pathway named in the narrative is actually present in the input table. That is a manual workflow, but it catches the most common failure mode – plausible-sounding genes that were never in the data. For provider failover, aisdk provides generate_text_fallback() for its own generation calls, but interpret() does not expose a fallback argument.

37.7.3 Practical Guidance and Pitfalls

Non-determinism. interpret() samples at temperature = 0.3 by default, so two calls with identical input will differ in wording and occasionally in emphasis. This is expected, not a bug. It has a direct consequence for reproducible builds: Quarto’s chunk cache (cache: true) is what keeps the published page stable – the LLM call runs once and its output is reused on later renders. Clear the cache and you will get a different report. If you need the exact same text in two places, cache the object and reuse it.

Unsupported entities. The model is instructed to ground claims in the supplied table, but it can still produce incorrect output. Before quoting a report, check that every gene named in the narrative appears in the geneID (or, for GSEA, core_enrichment) column and every pathway named appears in Description. If add_ppi = TRUE, identify the cited edges as STRING evidence, not measurements from the experiment.

n_pathways. Only the top n_pathways terms (default 20) are sent to the model, ordered by adjusted p-value (p.adjust, falling back to pvalue). Raising it gives the model more to work with but dilutes the signal and enlarges the prompt; lowering it forces a tighter focus. For a compareClusterResult, interpret() splits the result by cluster and returns one report per cluster, so the number of calls – and the cost – scales with the number of clusters, not with n_pathways.

max_tokens. The default is 8192. Reasoning models spend part of that budget deliberating before they emit the JSON, and if they run out, the reply is truncated and cannot be parsed; the symptom is a warning mentioning finish_reason: length and a placeholder report. If you hit it, raise max_tokens (the diagnostic suggests 16384 or more) or switch to a model that does not reason before answering.

Seeing the cost. interpret() returns only the parsed report; token usage is not part of the returned object. Run with verbose = TRUE to print the raw response and the prompt/completion/total token counts – the practical way to watch spend while you tune n_pathways and max_tokens.

add_ppi. Setting add_ppi = TRUE queries STRING for the genes in the top terms and injects the edge list into the prompt, which lets the model identify functional modules from individual genes. It requires network access, adds latency, and is a second failure point; the query is wrapped so that a STRING outage degrades to “no network evidence” instead of an error. Leave it at its default (FALSE) unless module-level reasoning is what you need.

gene_fold_change. Passing a named numeric vector of log fold changes adds the direction of regulation to the prompt. Note the limitation: the helper intersects your vector with the genes in the result’s geneID column, and a gseaResult table has no geneID column (it carries core_enrichment instead). So gene_fold_change is used for over-representation results (enrichResult, compareClusterResult) and silently ignored for GSEA results – which is harmless, because a GSEA result already encodes direction in the sign of its enrichment score.

Ranking. For over-representation results the terms are ordered by p.adjust; for GSEA the direction the model sees is the sign of NES. If your GSEA ranked list was built so that positive means “up in the condition of interest”, say so in context – otherwise the model has to guess the orientation.

Treat the output as an unverified draft. Check every gene and pathway named in the narrative against the input table; then assess whether each mechanistic statement has supporting evidence.
